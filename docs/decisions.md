# Architecture decisions

## ADR-001: authority and first delivery

Accepted by the user; reviewed by GPT-6.1 Sol on high.

- SQLite is the transactional source of truth. Google Drive is a retryable archive destination, not a prerequisite for a committed turn.
- Existing Drive records remain unchanged pre-game references. No real baseline has been approved. The initial executable economy is an explicitly fictional demo.
- First delivery is one generated planet, one economic turn, a controlled ChatGPT handoff, an atomic save and successful historical restoration. Four map levels and additional systems follow that gate.
- Use Python/FastAPI on Linux and a thin frontend. One process owns writes. No microservices or additional database infrastructure yet.

## ADR-002: controlled import and deterministic rules

Reviewed by GPT-6.1 Sol on high.

- Export a versioned decision packet. ChatGPT returns structured orders and narrative. An authorized operator imports, previews and commits the JSON.
- The backend recalculates results; imported balances have no authority. Preview does not write. Commit rechecks the source revision and calculates again.
- Exact proposal envelope: `schema_version`, `rules_version`, `base_turn`, `base_hash`, `submission_id`, `orders`, `narrative`. Reject unknown fields and non-integer allocations.
- Demo `economy-v1` applies one-turn assignments: technicians produce two energy; productive miners are limited by available energy, consume one energy and produce two ore; farmers produce three food; people consume one food each; shortages reduce population by the shortage capped at population. These are fixture rules, not Warhammer lore or real campaign canon.
- Generation has independent domain sub-seeds. Persist original geography and IDs. Never regenerate established state on reads.

## ADR-003: commit, restore and exposure boundary

Reviewed by GPT-6.1 Sol on high.

- Three initial tables: campaigns, immutable snapshots and outbox. Full snapshots are sufficient for v1.
- Canonical JSON and SHA-256 identify the versioned full-state envelope. Private hashes and seeds are not player API fields.
- `BEGIN IMMEDIATE` commits snapshot, current pointer and archive job together. Immutable snapshot triggers reject changes and deletion.
- Check existing submission IDs before stale-base checks. Identical retries return the previous commit; different content using the same ID conflicts.
- Restore creates a new branch from an existing snapshot and leaves the original campaign and entity IDs intact. Use SQLite's backup API for backups.
- Explicit public response projections exclude GM secrets, seeds and full raw state. All admin endpoints require a configured bearer token, with no default credential.
- Initial execution is loopback-only. Remote hosting requires audience authentication and TLS. Protecting secrets from the Linux operator requires a separately operated GM vault.
- Archive synchronization is pending/disabled without configured server-side credentials and an authorized archive folder. No source documents are rewritten automatically.

## ADR-004: isolation, bounded snapshots and integrity

Reviewed by GPT-6.1 Sol on high after inspecting the initial implementation draft.

- Submission identity is scoped to `(campaign_id, submission_id)`; no cross-campaign retry lookup. Different content with the same identity conflicts.
- State carries only its latest outcome. Prior outcomes are already retained in immutable snapshots; avoid quadratic growth from cumulative outcome arrays.
- Provincial population is unknown in v1. Planet population alone drives the fixture economy until a conservation-preserving regional distribution module is approved.
- Verify stored envelope checksums on state reads, preview, commit, export and restore; fail closed on mismatch. Restore also checks supported schema/rules and state invariants before creating a branch.
- Player responses also allowlist nested map, planet and province fields. Bounded paginated history returns summaries; load geometry only for the selected snapshot. Bound actual streamed administrative request bytes before JSON decoding, including requests without Content-Length.

## ADR-005: PostgreSQL authority and explicit legacy migration

Accepted following the user's explicit PostgreSQL requirement; reviewed by GPT-6.1 Sol on high. This supersedes the SQLite authority choice in ADR-001 and SQLite-specific transaction instructions in ADR-003. Existing decisions remain historical records.

- PostgreSQL is the sole authoritative write path. Use psycopg 3 and direct SQL, without an ORM or another persistence framework. Configure a server-side database URL; never fall back silently to SQLite. Keep transactions short and close connections explicitly.
- A commit locks its campaign row with `SELECT ... FOR UPDATE`, checks campaign-scoped submission identity before stale-base checks, validates/recalculates, then atomically inserts snapshot, changes current pointer and inserts outbox job. Concurrent identical submissions return the prior result. Different commands using the same submission ID conflict. Different campaigns need not serialize.
- Preserve immutable snapshot triggers, supported-version checksum validation and branch restores. Add a monotonically increasing snapshot sequence for pagination/ordering; it is not part of the historical checksum. Replace SQLite rowid ordering. Use a same-campaign constraint for current pointers where practical.
- Apply numbered PostgreSQL migrations. SQLite is only an explicit read-only legacy input. A migration CLI first backs up the source, verifies every source snapshot, rejects a nonempty target by default, then imports in one PostgreSQL transaction: campaigns with null pointers, snapshots in historical order, branch/current pointers and outbox. Preserve IDs, version strings, state/command contents and existing hashes exactly. Never regenerate geography or silently replace a campaign. Produce a counts/current-pointer verification report.
- PostgreSQL tests are authoritative: concurrent submissions, stale rejection, transaction failure after snapshot insertion, outbox failure rollback, historical restore, source-to-target verification and actual PostgreSQL backup recovery. A database connection failure leaves operations unavailable; it does not switch stores.

## ADR-006: retryable, public-only Drive archives

Reviewed by GPT-6.1 Sol on high. The desired real archive folder name is `Wold — Campaign Archives`; its folder ID and credentials remain deployment configuration. Demo archives require a separate destination, such as an isolated Demo subfolder. Existing source Docs/Sheets are unchanged.

- Use a small Drive v3 adapter and a fake adapter. Initial credentials may be an explicitly configured server-side access token; do not assume connector credentials are available. No token/folder means disabled or pending, not a failed database commit. Never print credentials or raw provider error bodies.
- Extend outbox through a migration with destination folder, projection version, frozen public payload bytes/checksum, lease owner/deadline and durable remote file ID. Claim an eligible job using `FOR UPDATE SKIP LOCKED`; persist its lease and increment attempts, then commit before network I/O. Expired claims are eligible for retry. Only the current owner may acknowledge or change job status.
- Freeze a versioned allowlisted player archive envelope from a checksum-validated snapshot: campaign ID/kind, opaque snapshot ID, turn, stored schema/rules versions, timestamp and public projection. Its hash is a public-payload checksum, never the private state hash. Exclude seeds, hidden entities, GM notes, private source references, raw commands and undisclosed future results. Freeze destination and bytes once; later configuration/projection changes do not redirect or alter the job.
- Dispatch `archive-player-v1` for world-v1 and `archive-player-v2` for world-v2; keep both projection implementations. Access-token expiry leaves a retryable provider-auth failure. OAuth refresh is optional and uses explicitly configured server credentials; never claim refresh or live connection merely because the adapter exists.
- Reserve a Drive file ID using `files.generateIds`, durably store it under the lease before uploading, then create immutable canonical UTF-8 `application/json` bytes with that ID. If allocation races lose the lease, discard the unused reserved ID. Retry the same stored ID after upload failures, conflicts or a crash before acknowledgement.
- Verify downloaded bytes against the frozen checksum and verify the parent folder, identity metadata and MIME type before marking verified. Existing wrong content/folder is an error; never overwrite or delete it automatically. A concurrent retry may see a create conflict and then verify the same file. Demo and real folder IDs must differ; bind jobs to campaign kind. Verified archives are not raw database backups and cannot restore GM secrets.
- Provide one-shot CLI synchronization with a bounded limit; no scheduler is required for correctness. Public status exposes pending/uploading/verified/error without private error text. Fake-adapter gates cover absent configuration, secret markers, upload failure, crash after upload, expired/concurrent claims, wrong content/parent, and destination changes. Live synchronization is only claimed after configured Drive verification.

## ADR-007: persistent hierarchy and version-safe public views

Reviewed by GPT-6.1 Sol on high. Introduce an explicit new `demo-v2` campaign using `world-v2` / `demo-v2`; do not silently upgrade or overwrite the existing v1 demo. V1 snapshots remain readable, restorable and resolvable by their original rules. Hashing, validation, projection and resolution dispatch by stored schema/rules versions.

- Branch identity clarification: `_private.campaign_id` is the active campaign's namespace for allocating new entities. Restore changes that metadata to the new branch ID and preserves every existing entity ID, seed, generator configuration and geographical value. It does not regenerate the world. Validate this namespace against the snapshot envelope's campaign ID. Allocate new IDs from a canonical tuple of active campaign ID, submission ID, action index and entity kind (SHA-256 is the lean collision-resistant encoding); derived children use their parent's ID plus kind/ordinal. Do not parse a mission's trailing text or append ad hoc collision suffixes. Existing IDs remain unchanged. No additional event-namespace field is necessary.

- Keep normalized entity lists inside immutable JSON snapshots; avoid another entity storage framework. A small fixed demo has one region, two sectors, three systems and four planets, with two owned settlements on the home planet and a separate fixture adversary. Persist generated nodes/geography once. Derive independent seeds from campaign seed, stable parent ID, domain, generator version and ordinal; keep seeds private. Existing entity IDs survive restores and moves.
- Map views are Galactic (visible sectors grouped by region), Sector (visible systems), System (visible planets) and Planet (surveyed geography). Nodes have stable ID, parent ID, kind, coordinates and knowledge state hidden/detected/surveyed. Detected nodes expose only an allowlisted silhouette; surveyed nodes expose permitted geography. Do not generate on reads.
- `GET /api/player/campaigns/{id}/map?level=...&node_id=...&snapshot_id=...` returns bounded visible nodes and links. `GET .../systems?section=...&snapshot_id=...` supplies each functional management section. An omitted snapshot means current; a specified snapshot must belong to the authorized campaign. Historical views use that snapshot's knowledge only. Unknown/hidden IDs return the same 404 response. Filter before counts, links, summaries, pagination and archives.
- Owned records use verified values. Foreign records use allowlisted persisted intelligence with observed turn and confidence, not live hidden fields. Static surveyed geography can remain verified. Unknown requested metrics are null with confidence unknown, never invented zeroes. Public histories return economic/budget/outcome summaries; selected map requests load geometry.
- Exact hierarchy fixture: one galactic root and one known region; Hearth sector surveyed and Frontier sector detected. Hearth system surveyed and Glimmer system detected belong to Hearth sector; Dusk system hidden belongs to Frontier. Reach planet surveyed and Ash planet detected belong to Hearth system; Haven planet hidden belongs to Glimmer; Veil planet hidden belongs to Dusk. Persist Hearth-Glimmer and Glimmer-Dusk adjacency; expose an edge only when both endpoints are visible. Detected labels are generic; actual hidden names/coordinates/details remain private. Surveying reveals immediate children as detected. Independent seeds supply bounded coordinates/geography; reads never fill in missing nodes.
- Province overlays use recorded location IDs: owned civilians plus owned ground soldiers and docked crews in that province for local population, completed facilities for infrastructure, eligible visible military/intelligence for military, and settlement unrest for politics. Counts are local, never the entire planet repeated in each province. Traveling crews/settlers remain in owned global totals but not province totals. Uninhabited surveyed owned provinces may report verified zero; foreign or undiscovered population remains unknown without intelligence. V1 provincial population remains unknown. Geography and overlay values always come from the same selected snapshot.
- Procedural completion: retain fixture names/counts/IDs but derive every map node's integer position from its parent/domain/version/stable-ordinal sub-seed. Stable grid slots with seeded jitter prevent overlaps without traversal-dependent randomness. Generate and persist all four planets' geography at initialization. Add one stable-ID central star and belt per system, and one moon per planet, with seeded class/radii/coordinates; no additional economy subsystem. Initially Hearth's star/belt are surveyed, Reach's moon detected, and bodies under undiscovered parents hidden. System/Planet responses expose only recorded permitted bodies; frontend decoration must not invent a central star or hidden child count. Exploration changes knowledge, not established geography. Test sub-seed/order reproducibility and exclusion of markers in all private geography.

## ADR-008: connected fictional demo-v2 mechanics

Reviewed by GPT-6.1 Sol on high. All following values are fixture rules, not real campaign canon. Deliver the connected engine in bounded stages: production/construction/budget/logistics; research/military; diplomacy/intelligence/exploration/colonization. Each completed stage must have working actions and outcomes, not placeholder tables. Freeze this catalog before implementation; any material rule change requires a new recorded rules version.

### State and handoff

- State lists: nodes, settlements/accounts, facilities, projects, units/fleets, shipments, factions/treaties, expeditions and characters/intelligence. Keep only latest outcomes and budget/production summaries; historical snapshots retain older ones. Continue the existing outer proposal envelope. V2 `orders` contains `allocations` and `actions`; at most 32 actions, strict type-specific fields, existing authorized IDs and bounded nonnegative integers. No balance/stat patches. Created IDs derive from campaign/submission/action index.
- Each allocation supplies settlement ID plus farmers, miners, technicians, machinists, scientists, builders, refiners and drillers. Their sum cannot exceed civilians after recruitment/transfers. Assignments last one turn. Costs and reservations process in submitted action order on a working state and may never overspend; failed proposals roll back completely. NPC standing allocations are explicit private fixture inputs, not frontend calculations.
- Owned opening population is 1,200 humans, split 900/300 across two settlements before assigning ten civilians to the starting transport crew. Credits start at 200 per owned settlement; fixture inventories include metals 100 and promethium 200. Persist all other starting quantities and facilities in a deterministic fixture manifest. Counts distinguish civilians, soldiers, crew and in-transit settlers; transfers cannot create humans. Foreign fixture population is excluded from owned totals.
- Fixture manifest: Forge and Outpost occupy the first two stable-ID provinces containing land on Reach. Forge has 890 civilians and its docked transport ten crew; Outpost has 300 civilians. Forge/Outpost stocks respectively: food 6000/2000, ore 1800/600, energy 3000/1000, materiel 100/50, data 20/10, metals 100/100, promethium 200/200, credits 200/200. Forge starts with two farms and one each mine/generator/factory/refinery/promethium well/lab/depot; Outpost one each farm/mine/generator/depot. Four owned characters have engineer/steward/general/scout roles and no assignment. Policies start tax one, welfare false, growth false. A contacted fictional adversary occupies the third land province, with one observed ten-soldier ground unit and one ten-crew/strength-ten fleet. Its civilian population is twenty, standing workers fourteen farmers/two technicians, and separate persisted accounts; its private resources are not player aggregates. Initial observed intelligence permits testing battles while its economy stays private. Adversary trade stocks food 100/ore 100/materiel 50 and credits 1000 are distinct from settlement accounts. Transport/fleet strength represents surviving combat crew in this fixture; battle casualties also remove those crew from population counts.

### Catalog and typed actions

- Production: one active farm/mine/generator supports 300/100/100 workers. Each farmer produces three food; technician two energy; productive miner consumes one energy for two ore. Refineries support ten refiners, each consuming two ore/two energy for one metal. Promethium wells support ten drillers, each consuming one energy for two promethium. Factories support ten machinists, each consuming two ore/one metal/one energy for one materiel. Labs support ten scientists, each consuming one energy for one data. Inputs limit productive workers deterministically; nothing becomes negative.
- `build(settlement_id, facility_kind)`: farm, mine, generator, factory, refinery, promethium_well, lab, depot, habitation or orbital_battery. Base cost twenty ore/ten materiel and ten builder-work; battery additionally costs twenty metals. Builders supply one work each. Completed facilities become usable next turn. Habitation adds 200 housing to base capacity 1,200 per settlement. Batteries contribute two defensive power to same-system fleet battles.
- `set_policy(settlement_id, tax_rate, welfare, growth_enabled)`: tax rate is 0..2; tax income is floor(civilians/100) times rate. Rate two adds one unrest. Welfare is persistent: when five credits can be paid that turn it reduces unrest by two; otherwise it has no benefit and records unmet spending. A food shortage adds five unrest; clamp 0..100. Optional growth occurs after feeding: with civilians positive and food at least twice civilians, births equal min(max(1,civilians//100), housing free, food//2), consuming two food each.
- `dispatch(source_id, destination_id, resource, quantity)`: owned settlements on an approved route; aggregate resource units per source/turn cannot exceed twenty per active depot. Deduct source immediately, retain cargo in a shipment, deliver next resolved turn. Logistics-I raises capacity to forty per depot. Food, ore, energy, metals, promethium, materiel and data are supported cargo; transported people use colony missions.
- `research(settlement_id, technology_id)`: logistics-I or industry-I, each costing twenty data, advancing by at most five data per turn. Industry-I raises factory capacity to fifteen. Completion applies next turn. No invented research prerequisite graph.
- Research spends twenty data in total through progress installments of at most five per turn; starting a project does not additionally charge twenty upfront. Persist spent/progress values so restore/retry cannot pay twice.
- `recruit(settlement_id)`: transfer ten civilians into a ten-soldier unit, pay ten materiel/ten credits. Units and crews consume food; units additionally owe ceil(strength/10) energy and credits each turn. Unpaid upkeep halves readiness. Starvation removes civilians first, then soldiers/crew/settlers by stable ID; record deaths and prevent duplicate population counts.
- `attack(unit_id, target_id)` / `fleet_attack(fleet_id, target_id)`: known hostile co-located ground units or same-system fleets. Each participant may fight once per turn; new units cannot attack immediately. Power is max(1,floor(strength*readiness/100)) plus assigned general and eligible orbital defenses. Apply simultaneous casualties min(strength,ceil(opponent power/10)); defeated entities have zero power and are inactive. Backend calculates all losses.
- `build_transport(settlement_id)`: twenty metals/twenty materiel/fifty credits, twenty builder-work; transfer ten civilian crew on completion, stalling if unavailable. Transport strength is ten and settler capacity 100. `fleet_move(fleet_id, destination_system_id, source_id)` requires a known adjacent system and colocated fuel source, spends five promethium, arrives after two turns. Moving fleets cannot fight or start another mission.
- `colonize(fleet_id, source_id, target_planet_id)`: idle transport at origin, surveyed unoccupied planet in the same or adjacent known system, 100 available civilians. Transfer settlers into a mission; reserve 400 food cargo; spend twenty ore/ten metals/ten materiel/twenty credits/five promethium. Arrive after two turns, feeding settlers from cargo while in transit; found a stable-ID settlement on an eligible persisted province with remaining cargo food, farm and depot. Fleet stays at destination. Costs replace an infrastructure project; colonization creates no population.
- `treaty(faction_id, operation)` proposes/accepts/rejects a trade agreement with a contacted faction. Pending proposals do not activate benefits. Authorized GM acceptance is explicit and audited. `trade(source_id, faction_id, resource, quantity, direction)` requires an active treaty and transfers stock and credits without negative balances. Fixed prices: food one, ore two, materiel three credits; persistent faction inventory and credits limit transactions.
- `explore(source_id, node_id)`: detected target with a known parent; pay two energy/one data, finish after two turns, survey target and detect its immediate children. `investigate(source_id, entity_id)` requires a detected/contacted entity, costs one data/five credits, finishes next turn and stores only approved intelligence fields with observed turn/confidence. Completed discoveries are recorded revisions; projected future discovery contents remain private.
- `assign(character_id, target_id)` assigns each known owned engineer/steward/general/scout to one owned settlement/unit/fleet. Effects are respectively one additional builder-work when builders work, one additional tax credit, one combat power, or exploration energy cost reduced to one. Gain one experience when actually used; no arbitrary stat-edit action. Changing assignment removes its previous effect.

### Resolution, summaries and gates

- Fixed phase order: arrivals/discoveries; validated paid actions/policies/assignments; tax and production; construction/research; feeding, permitted growth and upkeep; simultaneous battles; unrest/outcome/public summaries; immutable commit. Units, facilities and technology completed this turn become usable next turn. Feed colony passengers once per turn and transfer remaining cargo exactly once on arrival. Record per-phase inputs/outputs without copying cumulative histories into state.
- Public economic summary supplies owned civilians/total humans, stocks by resource, production/consumption/transit/losses and latest turn. Budget supplies opening credits, tax and trade revenue, actual recruitment/trade/welfare/maintenance spending, unmet upkeep and closing credits. Historical charts use these stored values, not frontend simulation. Foreign holdings are not included in owned totals.
- Reconcile closing treasury exactly to opening plus tax/trade receipts minus actual recruitment/build/trade/welfare/upkeep credit payments. Construction recipes with no credit component do not invent one. Credits moved between owned accounts are transfers, not new revenue. Housing and growth limits apply separately to each settlement; aggregate housing cannot bypass a local cap.
- Gates: production input limits and labor competition; construction timing; tax/budget reconciliation; shipment conservation/duplicate delivery; population conservation across recruits/crew/colonies plus explicit births/deaths; technology timing; welfare affordability; simultaneous combat; capacity/fuel/blocked moves; hidden intel/old-history exclusion; stale/duplicate orders; restore exactness. Run interconnected long-turn fixtures against PostgreSQL and measure snapshot growth/latency. Real pre-game remains unknown and cannot resolve until approved baseline/rules exist.

### Population and travel clarification after the initial v2 review

This replaces duplicate settlement military/traveler buckets and ambiguous feeding in the initial prototype, before the v2 fixture release. It also refines the fleet movement command above. Historical v1 rules are unchanged.

- Authoritative people are settlement civilians, ground-unit strength, fleet crew, and colony-mission settlers, each exactly once. Fleet strength equals surviving crew in this fixture. Do not persist settlement soldiers/crew/settlers as additional balances: derive public local fields from actual locations, and derive owned global humans across all owned ledger entities. Travelers are included globally and excluded from province totals. Transfers and combat never create or double-remove people.
- Recruitment transfers ten civilians into a unit. Transport completion transfers ten civilians into crew and retains an incomplete project when civilians are unavailable; it must not discard the stalled project. Food shortage removes civilians, then local ground units, then local crews in stable ID order. Fleet casualties remove crew once and set strength to the remaining crew.
- Fleet movement/colonization records origin, destination, departure turn and arrival turn and makes the fleet busy. Busy fleets cannot attack or start another movement/colony mission. Docking and fuel source must be physically colocated. No stale home-settlement link is retained as a physical location after departure; a funding reference is separate. Zero-strength/crew ships cannot create a colony.
- Travelers consume one ordinary meal from their origin on the departure turn, not cargo. Subsequent travel ticks consume cargo before arrival. Ephemeral already-fed groups prevent a second destination meal on the arrival turn. Colony cargo 400 feeds 100 passengers plus ten crew on two travel ticks, leaving 180 food transferred to the settlement; passengers become civilians, crew docks there, and the mission disappears. No origin feeding of passengers after departure, no fleet/mission cargo double consumption, and no duplicate arrival.
- Fleets have authoritative onboard food/promethium stores funded by transfers. The starting transport's food 100 and fuel 20 are transferred from Forge: Forge opening food 5900 and promethium 180, preserving the previously specified global inventories. `resupply_fleet(source_id,fleet_id,food_quantity,promethium_quantity)` transfers bounded nonnegative amounts, at least one positive, from a same-system owned settlement to an idle owned fleet.
- `fleet_move` permits null source_id to use loaded stores; with a colocated source, load twice crew food plus five promethium, then burn five onboard promethium. Remote departures require enough onboard food for the ordinary departure meal and two travel meals. On arrival dock at an owned settlement if present; otherwise remain orbital without an old docking link and consume onboard food on future idle turns. Ground units alone owe the catalog's energy/credit upkeep; fleets consume food and paid movement fuel.
- Reset owned workforce assignments each turn, then validate every resulting assignment against civilians after transfers. Feed/population results precede queued combat. Both combat participants act at most once per turn; defeated/busy participants cannot fight. Readiness reflects paid ground upkeep, and eligible batteries enter fleet power. Store gross production separately from consumption so resource balances reconcile.
- Intelligence is a bounded current observation per entity plus the latest turn's discoveries. Do not append cumulative discovery lists inside each snapshot. Investigation must update permitted cached observations with observed turn/confidence; charging for another null/unknown placeholder is not a functioning investigation. Public foreign fields remain cached observations, never current secret fields.
- Approved fictional investigation observation: civilian range has width 100, with `min = floor(civilians / 100) * 100` and `max = min + 99`, confidence low and the completion's observed turn. Cache and disclose only this estimated range, observed location and timestamp; foreign exact civilians remains null. The twenty-civilian fixture produces an estimate of zero through 99. This does not establish any real campaign baseline or reveal foreign military/resources. Discovery observations and all nested outcome rows use explicit field allowlists.
- `deploy_unit(unit_id,destination_province_id,source_id)` supplies a one-turn direct march without a pathfinding framework. Require an owned surviving unit that is not new, moving or already acted; a different surveyed land province on the same planet; and an owned same-planet sponsor with an active depot. Reserve troop strength in shared depot transport capacity alongside resource dispatches. Pay strength food for travel cargo and ceil(strength/10) energy, with no additional credit fee. Record departure/arrival, destination and supply_source_id; the unit remains the sole population record. It eats one ordinary sponsor meal on departure and cargo on the next travel tick, arrives already fed, changes physical province, and is marked acted on arrival; combat can begin the following turn. Neither source nor destination stores a duplicate troop-population balance.
- Deployed stationary units use their same-planet supply_source_id for food and ordinary energy/credit upkeep; the sponsor is not their physical location. Active depot capacity supplies up to strength food per unit in stable ID order before allocating capacity to player dispatches. Record actual ration expenditure/capacity; exhausted depot/food means no free resupply, and unfed soldiers die after available unit food cargo. Ordinary units at their local owned settlement may eat locally without depot transport. A zero-strength unit cannot move or fight. Gates include natural deployment to the fixture adversary, movement/arrival action exclusion, shared capacity, ration losses, treasury/resource reconciliation and historical province totals.
- When a colonizer reaches zero crew/strength, make the fleet inactive and cancel every associated colony mission before arrival. Remaining mission passengers die once; record and remove remaining mission food and onboard food/promethium as resource losses. Do not recount crew casualties already recorded by combat/starvation. No settlement, cargo delivery or refund can follow destruction. Human/resource conservation includes these explicit deaths/losses.
- Combat may refresh a previously known foreign participant's cached surviving strength and known battle location with current observed turn/confidence. It must not expose unrelated holdings, hidden entities, confidential source data or unobserved readiness.
- Validate the resolved state before preview hashing, commit hashing/insertion and restore hashing/insertion, using its actual stored schema/rules version. Required checks: strict nonnegative integers (excluding booleans) for people, accounts, cargo, capacities and progress; complete supported resource keys; unique IDs across entities; valid typed parent/location/owner/project/mission/shipment/assignment references; known visibility enums and no visible child under a hidden parent; fleet strength equals crew and passenger load respects capacity; consistent busy destinations/timing; defeated entities inactive; and no duplicate settlement military/passenger balances. Validate the active campaign namespace on v2 reads and writes. Resolver accounting must reconcile humans to prior humans plus recorded births minus recorded deaths, and closing treasury to prior treasury plus actual receipts minus payments. Bounds permit documented sentinels such as acted_turn=-1, and signed net-change summaries; they do not permit negative resource balances. Reject invalid state before any authoritative pointer/outbox changes.
- Every persisted planet must already have its generated geography. Exploration reveals that saved geometry and fails closed if it is missing; it never regenerates a corrupt baseline. Typed location validation checks province membership in the referenced planet, fleet docking within its referenced system, supported facility/node kinds, housing/capacity integers, readiness/unrest bounds and exact policy types. Province troop totals use physical location, independently of their funding settlement. Already-fed arriving ground units do not eat a second local meal. Defeated ground units cancel movement, with remaining cargo explicitly returned to its sponsor or recorded as a resource loss.
- Reconcile every owned resource across settlement stocks, ship/unit stores, shipment cargo and colony cargo: opening plus gross production and external receipts, less recipe/meal/growth/research/action consumption, external transfers and recorded losses, equals closing. Internal dispatch/resupply/recruitment/colony transfers change ledger location only. Record transit meals and remote rations alongside local meals so summaries explain actual changes; do not hide unbalanced resource changes with an inferred adjustment.
- Aggregate reporting contract: `latest_outcome.resources = {opening, inflows, outflows, closing}`. Opening/closing contain every supported resource; categorized inflows/outflows contain only actual nonnegative integer amounts recorded at mutations. Inflow categories are production, taxes and trade. Outflow categories are action_costs, recipes, meals, growth, research, upkeep, welfare, trade and destruction. Initialize opening before arrivals. Gross production precedes recipe deductions; loaded food/fuel/cargo is an internal transfer, while burned fuel and eaten meals are outflows. Trade crosses the owned ledger boundary, taxes include the steward receipt, and food shortage consumes only food actually available. Reconcile every resource before commit and retain the independent treasury assertion. The player projection recursively allowlists resources and these categories.

## ADR-009: configurable private access and deployment

Reviewed by GPT-6.1 Sol on high. Implementation/configuration can finish without a domain or live Drive destination; external operation is only claimed after actual verification.

- `WOLD_ACCESS_MODE=local|private`, local default through a loopback-only launcher. Admin always requires `WOLD_GM_TOKEN`. Private mode fails startup without GM token; optional `WOLD_PLAYER_TOKEN` must differ, and `WOLD_PLAYER_CAMPAIGNS` is an explicit comma-separated allowlist without wildcards.
- Every player data route in private mode accepts GM bearer for all campaigns or player bearer only for permitted campaigns. Filter campaign lists before counts; resolve snapshot ownership before serialization. Unauthorized IDs return 404. Static login/assets contain no embedded campaign data. `/api/access` may expose only mode/login-required.
- Frontend keeps the bearer only in JavaScript memory and attaches it to every API request. Reload requires login again. No token in URLs, cookies, localStorage, sessionStorage or assets. Admin features remain GM-only. This avoids adding a session framework; there is no cookie-authentication CSRF surface.
- Deployment templates use systemd, a protected environment file, loopback uvicorn, Caddy TLS termination and automated PostgreSQL backups with tested recovery. Host/domain/certificates, database credentials, access tokens and Drive folder IDs are operator configuration, not default secrets. Browser QA must cover the user's macOS browser when available; another browser's success is not a Safari claim.
- Controlled JSON import remains the working ChatGPT handoff. Future authenticated MCP tools reuse the same packet/preview/commit pipeline and authorization; MCP is not required for current completion. Existing live campaign documents and unknown statistics remain untouched.

## ADR-010: map desktop shell
